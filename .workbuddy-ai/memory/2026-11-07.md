# 2026-11-07 — SSE auto-update feature + optimization

## What was built

Added lightweight automatic updates so HR sees employee-submitted OB forms and
employees see HR status changes without manual refresh. Free-tier safe.

### Architecture
- One SSE endpoint: `GET /api/updates/stream` (authenticated, per-tab).
- `UpdatesService` holds in-memory subscriber set; `publish({signal, audience?})`
  pushes to connected clients.
- In-process writes publish instantly via `ActivityLogService.logBy()` — zero
  DB reads on the primary signal path.
- Backstop poll every 60s (was 10s) using head-only probe: `select('id', { count:
  'exact', head: true }).gt('created_at', lastKnownTimestamp)`. Zero response
  body, just Content-Range header. ~1,440 reads/day (was 8,640).
- `ActivityLogService.logBy()` calls `UpdatesService.publish()` after DB commit.
- Client `LiveUpdates` component opens EventSource with `withCredentials`,
  invalidates mounted TanStack Query keys with version-gate + 5s throttle floor.

### Optimization pass (after user feedback)
Researched Supabase free tier (Nano: 60 connections, 250 IOPS, 500MB) and
Render free (sleeps after 15min). Applied:
1. Poll 10s → 60s (83% fewer DB reads)
2. Head-only probe (`head: true`) — zero response body
3. Timestamp watermark instead of row-id comparison
4. Stale-connection cleanup (drop after 3 missed heartbeats = 90s)
5. Client version-gate (skip duplicate/out-of-order signals)
6. Client 5s throttle floor (max 1 refetch wave per 5s)

### Free-tier constraints verified from docs
- Supabase Nano: 60 DB connections, 200 pooler clients, 250 IOPS, 500MB
- Render free: sleeps after 15min inactivity, 30-60s cold boot
- No Postgres LISTEN/NOTIFY, no Supabase Realtime, no per-row polling
- Rate limiter excluded for stream path (prevents reconnect death-spiral)
