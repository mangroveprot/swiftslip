## Retention — no 30-day floor, skeletons

- The owner decides the period: `RETENTION_MIN_DAYS = 1` (shared schema), `CHECK (days >= 1)` in
  0028, a 7-day chip back on the row. **Do not re-introduce a policy minimum** unless asked.
- Loading states: `RetentionSkeleton` for the whole panel, shimmer bar/count/status cells while
  `countsQuery.isPending`, and a two-line skeleton for the last run. Never print "— days",
  "counting" or "No cleanup has run yet" while a query is still pending — it reads as real data.
- `dayLabel(n)` handles "1 day" vs "3 days" everywhere the period is shown.
- The form-list badges require **enabled + the type ticked**; with `form_types = []` nothing is
  warned (nothing can be deleted). The settings page now says "No form types ticked" in the status
  column so this is never a silent mystery.
- Note for short periods: with `days < 7` every finished form of a ticked type is already inside the
  warning window, so all of them badge immediately — that is correct, not a bug.
- Badge labels: `Deletes in N days` (amber) / `Due for deletion` (red). The red one used to read
  "Deletes on the next cleanup" but overflowed the narrow Time Records cards (which have a thumbnail
  beside the text) — keep card labels under ~20 characters.
- Verified on all five lists (records/ob/loa/cos/ot) by mounting each route in the router harness.
- **Nothing is automatic, and the UI must say so.** There is no scheduler in the API; `run` is only
  reachable from `POST /admin/retention/run`. The word "Automatic cleanup" on the page made the
  owner think setting a short period would self-delete, so the label is now "Cleanup" with the note
  "Only when you press Run cleanup." Keep "automatic"/"auto" out of this screen.
- The owner had already applied the first `0028`, so the live DB kept `CHECK (days >= 30)` — the fix
  is `0029_retention_days_floor.sql` (drop any `days` check by definition, re-add `>= 1`).
- **Local SQL testing without credentials:** `initdb -D C:/tmp/pgtest/data -U postgres -A trust`,
  then run `postgres -D ... -p 55432` via `run_in_background` (a plain `pg_ctl start` gets killed when
  the shell exits), `psql -w -h 127.0.0.1 -p 55432 -U postgres -f file.sql`, then delete the folder.
  The machine's own PostgreSQL 18 needs a password we don't have; the scratch cluster needs none.
