# 2026-10-07

## OT preview rebuilt to the Word template's true geometry

The user reported the OT preview "is look shit". Root cause: the previous
`OtPreview.tsx` was laid out **fluidly at invented proportions** — a 860px
`max-width`, hand-picked `%` column widths, Arial 14px — so the on-screen form
and the form the app actually prints were visibly different documents.

Rebuilt against `public/ot_template.docx` using measurements taken from the file
itself, cross-checked against Word's own PDF render (see the verification method
in `MEMORY.md`).

### The findings worth keeping

- **Content box is 714px.** A4 11906 twips − `pgMar` left 540 / right 656 = 10710
  twips, and 1 twip = 1/15 px at 96 dpi. `@page ot` now reproduces those margins
  as 20.6 / 11.6 / 6.35 / 9.53 mm.
- **The logo is page-centred, not content-centred.** `word/document.xml` anchors
  it at `posOffset 2985135` EMU from the *page*, which works out to exactly the
  centre of the A4 sheet — and, because the template's margins happen to be
  symmetric in the other direction, to `margin: 0 auto` inside the content box.
  Size is `wp:extent cx=1590040` = 106px.
- **The OT value row has SIX cells, not seven.** Rows 5/6 of the table merge
  cells with `<w:gridSpan>`, but row 7 — the row `{#entries}` repeats — does
  not, so ACTUAL OT HOURS splits into FROM/TO and REGULAR SHIFT SCHEDULE is a
  single 255px column. Target tracks: 98.9 / 175.6 / 71.7 / 27.1 / 44.2 / 98.9.

### THE BIG ONE — Chrome will not honour sub-pixel table columns

The preview uses **CSS Grid, not `<table>`**, and this is not a style preference.

With `border-collapse: collapse`, Chrome derives column widths from the cells
and **floors each to a whole pixel**, ignoring `<colgroup>` entirely. The OT
table rendered as 136 / 242 / 99 / 37 / 61 / 137 instead of the template's
98.9 / 175.6 / 71.7 / 27.1 / 44.2 / 98.9 — every rule in the wrong place.

Things that **do not fix it** (all tried):
- `<col style={{ width }}>`, in every combination
- `width: 100%` on the table
- making the header `colSpan`s add up to 6
- tuning the asked-for widths to any sum (373 → 900px made no difference at all
  below 714, which is the tell: Chrome was never reading them)
- `box-sizing: border-box` vs content-box

**Explicit grid tracks take fractional px verbatim.** That is the fix. If a
future form preview must match a Word template to the pixel, reach for
`display: grid` with `grid-template-columns` immediately; don't spend an hour on
`<col>`.

### Scale-to-fit

The sheet renders at its true 714px and a `.ot-fit` / `.ot-fitsheet` pair scales
it to the preview column, mirroring `.loa-fitbox` / `.loa-fitsheet`. `.ot-fit`
carries the measured scaled height; `.ot-fitsheet` carries
`transform: scale(var(--ot-fit-scale))` with `transform-origin: top left` and the
true width. Both declarations are dropped by `@media print` so it prints 1:1.

Gotcha: `transform-origin: top center` leaves the layout box at the full 714px,
so the scaled sheet overflows the column and the wrapper reports the wrong
height. `top left` plus a separate height box is the arrangement that works.

Also: the `@page` variable must be declared on **both** `.ot-sheet` and
`.ot-fit` — the lightbox renders the bare sheet with no wrapper around it.

`PreviewLightbox` takes `sheetWidth`; OT passes `OT_SHEET_WIDTH` (714) rather
than the 688 default, or its "fit" maths is wrong.

## Superseded the same day — OT preview now follows the OB house style

The pixel-exact replica above was **wrong for the on-screen preview** and was
reverted a few hours later. The user's reference was the **OB preview**: fluid,
readable, and built the same way as the Word template.

What was wrong with the replica approach:
- 714px rendered into a 416px column scaled to ~0.58 → body text ≈6px. Unreadable.
- It required a whole parallel styling system (`.ot-sheet` in `styles.css`, a
  `.ot-fit`/`.ot-fitsheet` scaler pair, a `@page ot` binding) that **no other
  form in the app has**. Every other preview is inline Tailwind.
- "Accurate on paper" was never the complaint — the *preview* was.

**The OB idiom, which is the standard:**
- Root: `print-sheet mx-auto w-full bg-paper px-6 pb-6 pt-1 text-[13px]
  leading-tight text-ink shadow-sm ring-1 ring-border`, Calibri.
- Logo `w-[30%]` (a %, so it scales with the sheet), `text-[18px]` Eras title.
- **Each block is its own `border-[2.5px] border-ink` box with an `h-2.5` gap
  between them** — not one continuous table grid.
- Cells: `border border-ink px-2 py-1 align-top`; a `HeaderField`-style helper
  puts the bold label above the value. `bg-yellow-300 px-0.5` on the label the
  template highlights.
- Header rows: `style={{ backgroundColor: HEADER_FILL }}` with
  `HEADER_FILL = "#a6a6a6"` for OT (`#7f7f7f` for OB).
- Signatures: a thin label row with `border-b` over a tall names row.
- Footer: `mt-6 border-t-[3px] border-dashed border-ink`.
- No sheet CSS in `styles.css`, no scaler, no bespoke `@page` — it shares the
  default one with OB.

For print, everything then comes out right for free because `.print-sheet`
already stretches to the page width and drops its padding.

**Kept from the geometry work:** the six-column OT table. The template's row 7
(the `{#entries}` loop row) does NOT merge cells even though the header rows
above it do, so the value row has two separate ACTUAL OT HOURS columns.

### Headless rendering with real Tailwind

`src/styles.css` imports Tailwind v4 as a package, and `@tailwindcss/cli` is not
installed. Compile it with the Node API instead: `import { compile } from
"tailwindcss"`, pass the stylesheet and a `loadStylesheet` resolver, then
`compiler.build([...classes])`. The resolver gets the *bare package* ids
(`tailwindcss`, `tw-animate-css`) and must map them to their real entry files —
`readFileSync("tailwindcss")` resolves to a directory and throws `EISDIR`.

### Lesson: a union table param in the Supabase client needs EVERY member typed

`db.from(table)` where `table: "loa_forms" | "cos_forms" | "ot_forms"` builds a
union of the three table types. If even one member lacks the selected column,
the whole union collapses to `SelectQueryError<"column 'other_attachments' does
not exist on 'cos_forms'.">` and every `.select()/.update()` result becomes
`never`. Fix: add the column to **all** members' Row/Insert/Update in
`database.types.ts` (and a migration for any table that doesn't have it yet),
not just the one the feature targets.

Also: `qc.setQueryData(key, (prev) => prev ? {...prev, ...next} : next)` fails
typecheck once the query data grows a key `next` doesn't carry. The
`prev === undefined` branch has to be built out too — here
`{ ...next, others: [] }`.

Migrations 0017–0021 are still NOT applied in Supabase.

## OT form: AI assistant chat UI + tear-off line removed

The OB assistant already had a full server side; the OT one did too
(`ot-assistant.server.ts`, `chatOtAssistant` in `ot.functions.ts`,
`otChatInput`/`otChatReplySchema` in `shared/schemas.ts`) — but **no UI**, so it
was unreachable. Added `OtAssistantChat.tsx` (a port of `ObAssistantChat.tsx`
with OT copy and `ot-assistant-open` as the localStorage key) and mounted it in
`OtEditor.tsx` behind `canEdit`, plus `applyAssistantPatch` which merges the
reply's `Partial<OtForm>` + entries into local state so it auto-saves.

Also removed the dashed tear-off rule (`mt-6 border-t-[3px] border-dashed
border-ink`) from `OtPreview.tsx` — the user didn't want it.

### Pattern: form assistants are 4 files, and the server half can already exist

For each form `X` in {OB, LOA, COS, OT}: `src/server/services/X-assistant.server.ts`,
a `chatXAssistant` server fn in `src/api/X.functions.ts`, `xChatInput` /
`xChatReplySchema` in `src/shared/schemas.ts`, and
`src/features/<feature>/components/XAssistantChat.tsx`. When asked to "add the AI
integration" to a form, **grep for the existing server pieces first** — several
of these were built ahead of their UI and only need the chat component + an
editor mount.

## CORRECTION — COS never needed `other_attachments`; reverted

Earlier the same day I "fixed" a typecheck error by adding an
`other_attachments` column to `cos_forms` (migration `0021`, plus the type
entries). **That was the wrong fix and has been reverted** — COS has no
other-attachments card and should not have the column.

The real cause: `OtherAttachmentTable` is a union and `db.from(table)` is a union
of those table types, so a member missing the column collapses the whole chain to
`SelectQueryError`. The correct move is to **narrow the union to the tables that
actually have the feature** — now `Extract<AttachmentTable, "loa_forms" |
"ot_forms">`. Nothing else needed changing; typecheck passes with COS untouched.

Rule of thumb: when a shared service's union type breaks, check whether the newly
added member even belongs there before writing schema for it.
