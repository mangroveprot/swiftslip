## DTR "Save as PDF" dropped attachments — root cause and fix

Owner's screenshot: Windows Save As dialog + orange toast
"2 attachments could not be added to the PDF." The attachments looked fine in the
on-screen preview.

**Root cause (verified live, not guessed):** the DTR's files are on the Backblaze
B2 backend. A B2 presigned GET answers `Access-Control-Allow-Origin: null`
(OPTIONS 403), so `<img>`/`<iframe>` can *display* the file but browser
`fetch()` of the bytes is blocked. `web/src/lib/save-pdf.ts` fetches attachment
bytes for image flattening and PDF merging; when the fetch fails it pushes the
name into `skipped[]` and shows that warning. `downloadFromUrl()` failed the same
way. Supabase signed links send `ACAO: *`, so the bug only shows for B2 objects.

**Fix:** same-origin byte relay, not a CORS/CSP relaxation.
- `GET /api/files/attachment?url=…` (new, behind existing `authenticate`):
  `shared/src/schemas.ts` `attachmentProxyQuery`;
  `api/src/apps/files/{routes,controllers,services}` adds
  `FileService.attachmentBytes()` returning raw bytes with `private, no-store`
  + `nosniff`.
- Guard: HTTPS, host == configured Supabase host or B2 endpoint host/subdomain,
  path contains `FormAttachement/`, and a real signature (`?token=` for
  Supabase, `X-Amz-Signature` for B2). Access control stays where the signed
  link is minted (owner-scoped row / `requireApp('hr')`). Verified: real B2 link
  → 1 854 084 bytes `image/png`; foreign host / unsigned / wrong folder →
  `FORBIDDEN`; unauthenticated route → 401.
- `web/src/lib/attachment-file.ts` gains `attachmentBytesUrl()` and
  `fetchAttachmentBytes()` (with `credentials: "include"` — needed when
  `VITE_API_URL` is cross-origin, otherwise the relay 401s). Both `save-pdf.ts`
  fetches and the Download button now use it.

**Reusable lesson:** in this repo, any code that needs attachment *bytes*
(html2canvas export, jsPDF/PDF merge, blob download, canvas pixel reads) must
go through the same-origin relay. Cross-origin signed links are display-only.
`savePdfFrom("dtr-sheet")` clones only the sheet node, so `OtherAttachmentsPrint`
images are not double-added.

## Onboarding only ever showed once per browser

Owner: "can you fix the onboarding why is it didnt show up if im gonna sign in
again".

**Two root causes (not just the obvious one):**
1. `markOnboardingSeen()` writes `swiftslip.onboarding.seen:<id> = 1` to
   **localStorage** and nothing ever removed it → `needsOnboarding()` returned
   false on every subsequent login. Fix: `resetOnboardingSession()` clears all
   seen keys (localStorage) and step keys (sessionStorage), called after a
   confirmed sign-in AND on sign-out.
2. `needsOnboarding()` only tested `!profile.full_name.trim()` (plus a
   sessionStorage step key). A user who saved a name but skipped work details
   or signature could never see the welcome again even with the flag cleared.
   Fix: `gapCount(profileGaps(profile)) > 0`. Keep `hasSeenOnboarding()` first
   so skipping still lets them into the app for that sign-in, and keep the
   `readOnboardingStep() !== null` fallback so a complete profile sitting on
   the "You're all set" card is not bounced out on refresh.

**Third issue fixed while there:** `profileQueryOptions()` has a 5-minute
`staleTime`, so a different account signing in on the same tab could be judged
by the previous account's cached profile. `LoginForm` now calls
`queryClient.removeQueries({ queryKey: profileQueryOptions().queryKey })` after
the session cookie is confirmed, so `/choose`'s `ensureQueryData` refetches.

Also: `OnboardingFlow` initial step is now the first unfinished gap (via
`profileGaps(data)`) when there is no remembered step, so a returning user is
not asked to retype a name they already saved.

**Reusable lesson:** in this repo, "once per sign-in" state must be reset at
sign-in (covers expired sessions and account switches) **and** at sign-out
(covers leaving mid-flow). A bare localStorage flag means "once per browser
forever". All onboarding gates (`/choose`, `/_app`, `/hr`, `/admin`,
`/onboarding`) share `needsOnboarding()`, so one change covers every route.

Checks: `npm run typecheck` + `npm run lint` pass (0 errors, 6 pre-existing
warnings). 11 assertions in a `tsx` probe against the real `onboarding.ts`
with stubbed window storage — all pass. `ACTIVITY_LOG.md` top entry + Phase 9
checklist box added.

## Onboarding must exit through `/choose`, not a hardcoded route

Owner: "this says go to dashboard, but i dont want to, i want how the chooser
it works ... the chooser shows if there 2 or more apps if only one this is auto
open no more chooser".

**The bug:** normal sign-in goes `/` → `/choose` (which either shows the picker
for 2+ granted apps or redirects via `APP_HOME` for exactly one). But a first
sign-in with profile gaps was diverted `/choose` → `/onboarding`, and the Done
card then hardcoded `navigate({ to: "/records" })` with the label
"Go to Daily Time Record". So the chooser was skipped entirely on that visit.

**Fix:** `enterApp()` calls `clearOnboardingStep()` + `markOnboardingSeen()`
first (that flag is what stops `/choose` bouncing back to onboarding), then
`navigate({ to: "/choose" })`. Button label → "Continue". This was the ONLY
navigation out of the welcome.

**Reusable rule:** `/choose` is the single source of truth for post-login
destination. Never hardcode a landing route in a screen that can interrupt
sign-in (onboarding, forced password change, etc.) — return to `/choose` and
let its guard decide. Guards live in `web/src/routes/choose.tsx`:
`apps.length === 1 && !isExternalApp(only)` → `redirect(APP_HOME[only])`.

**Edge case left as-is:** a single granted app that is external (ticketing)
has no internal route, so `/choose` still shows one card. Auto-opening a
cross-origin host from a route guard would contradict that card's "opens in a
new tab" copy — needs an owner decision.

Also note: `UserManagement.tsx` was edited by a parallel agent at 10:16 with
unformatted JSX; applied whitespace-only Prettier there so `npm run lint`
could pass. Both typecheck and lint pass (0 errors, 6 pre-existing warnings).

## OB RETURN column — date on late returns

Owner asked "how is this overdue if the employee doesnt have return" with a
screenshot (`.ob-overdue-inspect.png`): Nov 7 OB, departure signed Nov 9, no
arrival, card says "Overdue by 2 days". I assumed the Overdue derivation was
the bug and asked. **Owner correction: "did you see the date of OB? if passed
on that this is overdue" — Overdue is correct and must NOT be changed.** The
only fix was the RETURN display. Lesson: when the owner states a derived rule
plainly, don't "fix" the rule; fix the presentation they point at.

Confirmed choices (AskUserQuestion): same-day = Date of OB; date source = HR's
signed `arrival_date`; apply to all RETURN displays (preview/print/PDF, HR
detail row, Word export). Delivered via one new shared helper
`web/src/features/official-business/lib/return-display.ts` —
`obReturnRowIndex` / `obReturnDisplay` / `obReturnText`. It reuses
`resolveExitSignoff().arrival` (which handles legacy rows without
`arrival_date` by falling back to `stampDate(arrival_signed_at)`) and compares
`formatMonthDayYear` strings. Docxtemplater runs `linebreaks: true`, so `\n`
becomes a Word line break.

**Reusable convention:** one display helper feeds `ObPreview` (the DOM that
`printSheet` and `savePdfFrom` capture), the HR review row and the Word token.
Never re-derive a printed value separately in those three places — that is how
they drift. `ReviewField` now has `subValue` for stacked read-only values.

**Left intentionally alone:** `HrObDetailPage` still prefills `arrivalDate`
with `date_of_ob`. HR must type the real return date for a late return. Rolling
it to "today" would be wrong when someone returned on time but was signed in
later. The Exit Clearance signature box still prints time + date side by side
by design (its label is "Date / Time of Actual Arrival").

### Correction 30 minutes later — same-day exception removed

Owner reopened a COMPLETED form (OB 11/07, arrival signed 12:00 PM on 11/07,
today 11/09) and asked "wheres the date and time here in return?" — preview
still showed only `12:00 PM`. Root cause of the miss: the "same-day" test I
implemented compared `arrival_date` to `date_of_ob`, but **Sign arrival
pre-fills `arrivalDate` with `date_of_ob`**, so those two values match BY
DEFAULT. The test could essentially never fire for a normal sign-off. Classic
case of writing a rule against a field that is seeded from the rule's own
comparison value.

Offered four behaviours; owner chose **"Show date once signed"** — no
same-day exception at all. `obReturnDisplay()` now returns
`date: isReturnRow && arrival.signed ? arrival.date : ""`; `dateOfOb` param
and the `formatMonthDayYear` comparison are gone. `ObPreview`, `HrObDetailPage`,
`word-export` just dropped the argument. Prefill deliberately unchanged (owner
did not pick the "use the real return day" option).

**Reusable lesson:** before comparing a user-entered value to a reference
value, check whether that field is *prefilled from the reference*. If it is,
the comparison is near-tautological and the feature will look broken in the
default flow. Also: when a user reports a feature "missing", verify with a
completed/default-path record, not only with synthetic edge cases.
